# Participant evidence-capture kit

> **This kit does not create evidence.** It tells the participant exactly what to record, screenshot, write, or request in order to complete the remaining personal requirements honestly. Replace every `[participant entry]` field only after doing the real action. Do not upload blank templates as if they were completed work.

## Capture rules

Use the actual participant-controlled account, device, browser, or camera. Keep the date/time and the relevant app/site visible where practical. Do not stage an old screenshot as a new event, generate a fake personal photograph, narrate a demo that was not actually run, or invent a reviewer response. Save raw files privately first; upload only the evidence that the assignment requests.

| Evidence type | What a valid record must show | Not acceptable |
| --- | --- | --- |
| Screenshot | Relevant screen, real account/session, and meaningful visible context | Cropped mockup, stock image, or AI-generated replacement |
| Screen recording | Continuous real interaction with the stated tool/site | Slides, edited montage, or a terminal output pasted as video |
| Personal reflection | A statement the participant has checked and can defend | An unreviewed first-person AI draft |
| Peer/mentor critique | The actual reviewer, feedback, and resulting change | Invented review or fabricated name/quote |
| Hours log | Real dated work periods | Reconstructed or estimated hours presented as observed |

## 2. Prompting, identity, image, and content evidence

For the prompt exercise, run the required prompts in the permitted participant-controlled tool. Save the original prompt and result for each iteration, then write the comparison in personal words. The published [prompt-ladder review draft](./week-02-prompt-ladder-review-draft.md) is a starting structure, not proof of a participant-owned tool run.

For visual identity and curation, save the actual chosen type/palette/mark decision, the real image candidates, the final selected set, and a genuine one-to-two sentence rejection reason for each rejected item when the brief requires it. If the brief requires a personal photo, use a real participant photo; do not substitute an AI portrait. The [identity proposal](./week-03-identity-kit-review-draft.md) and [image strategy](./week-03-image-curation-strategy-review-draft.md) are design guides awaiting that choice.

## 3. Automation, MCP, and agent evidence

The published local visual workflow and five source-packet records are reusable source evidence. If the portal requires a personal before/after time comparison, record it in this format instead of estimating it:

| Run | Start time | End time | Seconds | Result / exception |
| --- | --- | --- | --- | --- |
| Manual source-review baseline | `[time]` | `[time]` | `[computed]` | `[actual outcome]` |
| Workflow source packet | `[time]` | `[time]` | `[computed]` | `[actual outcome]` |
| Human review / decision | `[time]` | `[time]` | `[computed]` | `[actual outcome]` |

For MCP, capture three continuous, visible real tool calls in the participant’s connected MCP client. Each record should include the prompt/action, tool name, visible result, and what the participant checked. A written explainer cannot replace this proof.

For the Evidence Scout agent, record one unedited run of at least the required duration. The recording should show the allowed target path, the command/action, sources found, and output file; it must not expose secrets or hidden files. The [build log](./week-05-agent-build-log.md) identifies the permitted boundaries.

## 4. Website, phone, and critique evidence

Open the live portfolio on a participant-controlled phone—not a sandbox emulator. Capture the browser address bar, one project-filter interaction, and a short personal explanation of what changes in the page. Keep any LinkedIn, CV, booking, or profile action separate and only show it after the participant performs it.

For critique, ask a real person to review one named area. Keep their actual feedback and log the change:

| Reviewer | Date | Specific feedback | Change made | Proof link/screenshot |
| --- | --- | --- | --- | --- |
| `[real name or permitted role]` | `[YYYY-MM-DD]` | `[actual feedback]` | `[actual change]` | `[private or public evidence]` |

For hardening, record genuine browser/device checks and outcomes. The [hardening audit](./week-07-hardening-audit.md) is a technical starting point, but it is not a participant device test or independent human review.

## 5. Week 8 final-checkpoint evidence

Record a real **3–5 minute** continuous demo of the capstone or the required final project. Show the actual running system; explain one design decision and one real limitation on camera. Use the [demo script](./week-08-capstone-demo-script-review-draft.md) only as a run-of-show, not as a substitute for recording.

Use this final package log:

| Requirement | Participant evidence to add |
| --- | --- |
| Retrospective | Rewrite the [review draft](./week-08-retrospective-review-draft.md) in personally true first-person words. |
| Hours | Enter real dated hours in the portal and retain the actual confirmation. |
| Public story | Publish one genuine build-in-public/showcase post naming one real decision and limitation; paste its URL. |
| Live-site/domain requirement | Complete only the actual FlyRank-domain/profile action required by the brief, then verify it in a private window if requested. |
| Final review | Submit for review and retain the genuine pass/revise/sign-off outcome. |
